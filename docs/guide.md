# Nootify guide

[Back to the project overview](../README.md). Commands and file paths in this guide are relative to the repository root.

Nootify is a **single Go executable** with desktop, CLI, and background `serve` modes. The background job is managed as a per-user macOS LaunchAgent or Windows Scheduled Task. Its Go HTTP host directly calls the notification core; it also owns SQLite state, agent transports, session discovery/backfill, and settings. The Go/MyGo desktop host owns the native window, tray, menus, trusted UI assets, language preferences, service lifecycle, and updater. TypeScript is used only for browser UI code, compiled and embedded during the build. No Go runtime, stdio bridge, or notification-core helper processes are shipped. Production does not read Feishu history on a schedule.

There are two provider types, each supporting multiple named channels: **Feishu** (`feishu`) receives WebSocket events directly, and **Remote Nootify** (`remote`) connects to another node over authenticated gRPC. Channels offers three setup choices: **Feishu Bot** with manual credentials, **Feishu personal app** through QR registration, and **Remote Nootify**. Both Feishu choices use an application bot, not personal user-token messaging. Providers expose agent sessions, metadata, deletion, sending, replying, and acknowledgments through a shared API. Platform groups and topics are provider details. See [Providers and remote nodes](#providers-and-remote-nodes) and the [core protocol](provider-protocol.md).

The HTTP listener binds on all IPv4 interfaces at `0.0.0.0:9417` by default. Open `http://127.0.0.1:9417/` locally or the sidebar LAN link, `http://<LAN-IPv4>:9417/`, from another device on the private LAN for message-bridge logs and **encountered routing targets**. `/health` and read-only `/ui/*` page data are available to permitted browsers; every `/v1/` control endpoint requires the per-user bearer token. Host/origin/fetch-site checks prevent cross-site access and DNS rebinding. See [LAN access](#lan-access) for the peer and local-authority boundaries. The service routes input to existing Claude, Codex, or OpenCode clients and provides per-conversation notifications and cooperative reply inboxes for Trae and WorkBuddy. It does not call a model API directly.

Local settings changes and secret reads require an actual loopback peer, the UI header, and Host/origin/fetch-site checks. A browser opened on `http://127.0.0.1:9417/` can manage local settings directly without an authorization link; reloading preserves that access. Local processes are trusted, while LAN peers and cross-origin pages cannot gain local authority. The desktop uses an encrypted gateway automatically; to open that gateway in a local browser, run:

```bash
./build/nootify ui-url
```

Use the same `--state-dir` and `--port` as the service when they differ from the defaults. Source examples use the executable built at `build/nootify`; installed macOS users can use `/Applications/Nootify.app/Contents/MacOS/Nootify`, and Windows users can use the installed `Nootify.exe`. The CLI prints a private URL and keeps its trusted Go asset handler running until interrupted. The desktop runs that handler inside MyGo, without a child process. Its browser capability travels only in the URL fragment, is removed immediately, and stays in memory. Reloading a gateway page needs fresh CLI/native authorization; a direct loopback page remains editable after reload. There is no two-minute UI idle shutdown. Native mode monitors the actual handler and renews expired authorization. Daemon sessions still reclaim abandoned capacity after three idle minutes; the Go handler establishes a fresh verified session when needed. Validation failures stay encrypted and interrupted mutations are never automatically resubmitted.

Every authorized desktop/CLI gateway UI API read, write and directory stream uses authenticated AES-GCM frames on both browser-to-gateway and gateway-to-daemon paths. The daemon traffic key is derived locally from the private root key and a fresh, mutually authenticated HMAC transcript bound to one TCP connection; bootstrap transmits only public session ID/expiry and a MAC. Session/request/direction/frame bindings, replay checks and expiry reject substitutions. Interrupted mutations are not automatically resubmitted. No authorization cookie or persistent browser storage is used: cookies do not isolate TCP ports. The root bearer never enters page code or bootstrap HTTP, and gateway sessions cannot invoke `/v1/` control APIs. Encrypted gateway sessions never fall back to plaintext after an error. Direct loopback pages use ordinary same-origin requests, and direct LAN HTTP does not use gateway frames and is plaintext.

Routing lookup is lazy: only a message with a concrete adapter and session ID resolves that adapter's inbox or connects to its backend. The routing page retains the latest 1,000 encountered targets in SQLite across service restarts, including missing/archived/unavailable results; previously active targets show as unconfirmed until checked again.

Preview-only repositories fall back to the newest published prerelease. Missing installers, rate limits, and network failures leave usable release-page links without claiming a fixed latest version. ## Build and test

Requires the Go version pinned in root `go.mod`, plus Node.js and npm for browser compilation/tests only. The Go backend opens the existing `state.sqlite` with a pure Go SQLite driver; the notification core retains its private durable JSON store. From the repository root:

```bash
npm ci
npm run build
npm run check
npm test
go test ./...
go build -o build/nootify ./desktop
```

The build compiles only browser TypeScript and embeds HTML/CSS/JavaScript/fonts in the Go executable. Use `./build/nootify serve` for a foreground service, or pass a separate `--state-dir` and `--port` for isolated development. Native libraries are linked directly; no notification helper executable needs staging.

`npm test` discovers test files without relying on shell glob expansion, sets a three-minute default test timeout, and writes `.cache/test-results.xml` in JUnit format. Windows runs test files serially to keep full-sync SQLite fixtures and native compiler children within the hosted runner's disk and CPU budget; concurrency inside individual tests is unchanged. CI uploads that report for each platform and limits the test step to ten minutes as a separate guard against cleanup hooks that never finish. SQLite fixtures close databases and backend sockets before temporary-directory removal; bounded subprocess regressions cover Windows file locks and failed cleanup.

### Headless integration tests

```bash
npm run test:integration
```

This command builds the real Go host fixture, unified executable/CLI, and a native-core upstream test fixture, then runs two Go HTTP services with their notification cores linked in process. The upstream mocks only the external bot boundary; routing, authenticated gRPC, session operations, direct delivery completion, SQLite inboxes, acknowledgments and replies use production code.

Coverage includes independent broadcast to two downstream nodes, local ownership, source-event deduplication, full-reference reply return paths, metadata, process-restart replay, notification-session deletion, and EOF shutdown. The suite uses the cooperative Trae inbox transport and does not start an agent client.

No desktop window, tray, installer, browser, system background service, or Feishu connection is started. State and binaries live in a fresh private temporary directory; listeners use ephemeral numeric loopback ports. Runtime children receive a restricted environment, credentials are synthetic, and the runner removes owned processes/state on completion. Results are written to `.cache/headless-integration.xml`. CI runs an independent Ubuntu headless job and the same process suite on macOS/Windows before installer tests. Native GUI smoke remains a separate disposable-runner check.

## MyGo desktop application and system tray

The native **Nootify** app supports Apple Silicon with macOS 13.5+, and Windows 10/11 x64. Both distributions contain one Go executable with the background service, CLI, MyGo desktop, notification core, direct LAN HTTP access, and compiled browser UI. Its native window, web UI, and offline page follow the system's light or dark appearance, including changes while the app is open. It provides a menu-bar tray with **打开**, **设置**, **软件更新**, and **退出**. Closing the window hides it; quitting the desktop app leaves the independent daemon running.

Download an installer from [GitHub Releases](https://github.com/idy/nootify/releases/latest): on macOS, drag Nootify from the DMG to **Applications**; on Windows, run the x64 `-setup.exe` installer, which installs for the current user under `%LOCALAPPDATA%\Nootify` without administrator access. Windows uses the WebView2 runtime (the installer offers to install it if missing). The first launch automatically installs and starts the background service; later launches connect to it or start the existing platform job if needed. A healthy service keeps its process and connection. The compact native tray menu shows Open, one application status, Software Updates, Settings, and Quit. Service installation and recovery are handled automatically; advanced service controls remain available through the CLI rather than the everyday tray menu. The menu uses the system material and follows the macOS appearance.

The desktop app is single-instance. Opening it again restores and focuses the existing window, including when minimized or closed to the tray, without restarting the background service.

Automatic installation requires port 9417 to be free. On macOS, `~/Library/LaunchAgents/dev.idy.nootify.service.plist` must be absent; read-only disk images are refused, so keep the app in Applications. On Windows, a login-triggered task named `Nootify.Service.<user-SID>` runs without elevation for the current user. It runs the Go service in a Windows Job Object, so stopping the task drains the owned service run. Existing jobs are reused; an unrelated task or another installation's task is never overwritten. Keep the application at its installed path.

Windows stop and replacement wait for the owned job's kernel process count to reach zero. The existing task host listens for Windows session-end notifications through a hidden window and attempts a bounded drain, publishing completion only after its job is empty; that receipt also permits recovery when local sign-out retains the terminal ID. A private receipt certifies that exact run after its job name disappears. Recovery also accepts a recorded change in the Windows boot sequence or explicit Windows confirmation that the original interactive terminal session no longer exists. All job members share that session, so completed sign-out permits the next sign-in to recover within the same boot. A missing job name, an empty Scheduler instance list, or a different logon token alone cannot certify shutdown. Present or reused session IDs, session zero, denied queries, and unavailable session information remain unverified. Hibernate preserves the session; Fast Startup may retain the boot sequence but can still recover through verified session deletion. If an abrupt host exit remains unverified, sign out and back in or choose Windows **Restart**; reopen Nootify or run `service-start` if an explicit Stop disabled the task. For legacy or unreadable identity metadata, restart Windows before deliberately removing or repairing only `windows-runtime.json` in the private state directory; retain `provider-core/`, `state.sqlite`, `auth-token`, and the other settings.

When `~/.claude.json` exists, the installer selects its `mcpServers.lark` credentials as a legacy migration source. The core imports available credentials and eligible group bindings once into the `legacy-feishu` provider; it does not overwrite a later provider edit or deletion. The original file stays intact. Without a provider, local logs and routing observations remain available; add a connection on **Channels** to send and receive notifications. The MyGo webview disables generic privileged frontend bindings. Validated fixed navigation requests support the title row and the update bridge described under [Automatic updates](#automatic-updates-and-releases). Builds are ad-hoc signed and are not notarized; macOS may require allowing the first launch under System Settings > Privacy & Security.

### Build the desktop app

Requires the Go version pinned in root `go.mod`, plus Node.js and npm for the browser build. The native host pins [MyGo v0.8.3](https://github.com/egoist/mygo/tree/v0.8.3) and builds with `CGO_ENABLED=0`. Rust, Cargo, and the Tauri CLI are not build dependencies. macOS packaging uses the system signing and disk-image tools. Windows packaging uses a pinned, verified NSIS compiler; the installed application uses the system WebView2 runtime. Build each installer on its target OS.

```bash
npm run desktop:dev
```

For a signed release build, supply `NOOTIFY_SIGNING_PRIVATE_KEY` and `NOOTIFY_SIGNING_PRIVATE_KEY_PASSWORD` in the environment, then run the command below. The existing `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` remain fallback inputs so CI can preserve its existing signing identity; signing is implemented in Go.

```bash
npm run desktop:build
```

Before bundling, the build compiles browser TypeScript into `public/ui/`, embeds the UI/offline HTML/CSS/JavaScript/fonts, and links the backend, notification core and MyGo into one Go executable. Staging collects Go dependency licenses. macOS also includes tiny compatibility launchers and entry markers at the historical Node-era paths so installed 0.2.1 updaters can validate the bundle and forward service/CLI commands to the Go executable. These files do not include a Node runtime, production npm packages, or notification/VPN helper runtimes. `npm run desktop:stage` prepares browser assets and notices; `npm run desktop:test` runs the desktop Go package tests. Owned legacy LaunchAgents and Windows tasks are migrated only after exact path/identity validation and process draining. macOS releases from 0.3.2 retain the regular-file layout required by the running 0.2.1 updater. During its GUI handoff, legacy service commands preserve the original LaunchAgent registration so a failed upgrade can still restore the old app and service. The compatibility daemon entry runs Go directly; a later normal Start/Restart migrates the registration to the direct Go path. Both Node-era and Go-era macOS clients can use the signed updater without a manual replacement.

Outputs under `build/desktop/<target-triple>/` are `macos/Nootify.app`, the Apple Silicon DMG in `dmg/`, and `macos/Nootify.app.tar.gz` with its updater signature on macOS; Windows produces an NSIS `*-x64-setup.exe` installer in `nsis/`, with an updater signature. `--target` selects the supported target triple. `--package-version <semver>` overrides the packaged version for isolated installer fixtures; production version authority remains the root `package.json`.

### Automatic updates and releases

The installed app checks [the signed release manifest](https://github.com/idy/nootify/releases/latest/download/latest.json) 15–45 seconds after launch, then every six hours with ±30 minutes of independently sampled jitter. Failed checks retry after 10–20 minutes, and deadlines include time spent asleep. Development builds check only on request. Select **检查更新** under the tray's **软件更新** submenu or **设置 · 关于** for an immediate check. When a newer version exists, **安装更新 vX.Y.Z** appears directly in the tray's top-level menu; every page also shows a compact **更新 vX.Y.Z** button in the title row. Routine checks and an up-to-date result leave the title row clear; About retains the latest status and manual check action. Downloading starts only when installation is selected. Installation verifies the update signature and replaces the app. On macOS, it restarts the background service if its LaunchAgent runs this app's Go executable, then relaunches the app. Service controls, including queued Start/Restart requests, are serialized with the update's stop, replacement, rollback, and restart. If a canceled handoff stopped the service, recovery uses a separate bounded context; quitting waits for worker cleanup and recovery before exiting. On Windows, the installer validates a fully staged replacement, journals the prior running state, stops only this installation's task, and exchanges package-owned roots with recoverable backups. It restores a previously running service even without `/R`, preserves a deliberately stopped service, and uses `/R` only for desktop relaunch. Legacy Windows `/P /UPDATE /R` updater invocations remain passive: progress is visible, directory input is skipped, and success closes the installer and relaunches the app automatically. A normal Windows uninstall removes the task while retaining private settings. One fixed-width title-row button stays in place throughout the update: **更新 vX.Y.Z** becomes **下载中 42%**, then **安装中…** and **重启中…**; the tray's top-level install action also shows progress in place and stays disabled while busy. There is no second line or separate progress bar. Unknown-size downloads show **下载中…**; interrupted downloads retain the update and its retry action. A failed background recheck also preserves an already found update. Clicking the title-row status or the tray's **更新详情…** opens **设置 · 关于** for full version, download size, and error details; the tray keeps failures concise.

A successful macOS stop reports whether its job was actually loaded; cancelled and successful updates preserve a deliberately stopped service across GUI relaunch. The old bundle remains until the new GUI verifies its app identity, version, canonical executable/hash and one-use private receipt, then confirms loaded-window/tray readiness and a commit acknowledgment. MyGo's result-free relaunch is replaced in this update path by a bounded Launch Services supervisor after the old event loop exits. A proven launch failure or acknowledged abort permits ownership-checked service quiescence and rollback, reopening the original GUI with the same stopped policy. Missing quiescence or identity proof preserves both bundles without an age-based sweeper. Later explicit Start remains available. A partial owned stop records the exact process PID/start identity in the current desktop manager after a proven LaunchAgent unload. Recovery rechecks ownership and waits for that process before starting again; it does not grant authority to a foreign or ambiguous registration. If both bounded stop/recovery attempts fail and the desktop exits, the in-memory receipt is lost and later launch uses the ordinary ownership/port checks. Replacement rechecks the original app directory immediately after the stop. If the replacement starts only partially, rollback first stops/drains it; an unverified stop preserves both bundles and blocks unsafe restart/exchange.

Windows updater launches use exactly `/P /UPDATE /R`. Retained installer images live under Nootify's user cache, with a pending handoff receipt. NSIS acknowledges opening the image; a later desktop start removes only acknowledged, unlocked known files and then the empty directory. Pending handoffs, locked files, symlinks and unexpected files are retained. Installer preflight refuses changed registered destinations and foreign, incomplete, unregistered or reparse-point payload directories. The embedded stdlib-only `nootify-installer-stage.exe` verifies the extracted SHA-256 manifest before service shutdown, journals same-volume exchanges and restores old roots/service state on failure. Enabled and running task state are saved separately: an enabled idle task stays enabled without being started. An interrupted exchange or rollback is replayed on the next installer attempt; persistent filesystem/service errors retain the journal and backups for recovery. A lone safe initial `journal.next` can be recovered before journal publication. Interrupted fresh installs require a matching private HKCU pending target/token and fresh journal receipt; arbitrary unregistered journals grant no ownership. A string-or-missing partial pending receipt is cleared before the destination lock without accessing the old drive; complete pairs, denied reads and malformed registry types remain protected. Uninstall quarantines package roots before irreversible removal and retains its executable, registration and removal journal on failure, so an independent gateway's runtime lock produces a retryable refusal. The helper never treats private state or unknown files as payload. Service commands run from a trusted Windows system directory rather than NSIS's plugin directory, whose native `System.dll` can shadow a .NET compiler reference in older service scripts. New service scripts additionally compile their management types with explicit framework assembly paths; this protects both legacy upgrades and later invocations without changing task ownership checks.

For installer diagnosis, `NOOTIFY_INSTALLER_DIAGNOSTICS` can name an existing caller-owned output directory. NSIS records fixed phase markers while preserving its Errors flag; each helper writes a new categorical JSONL report with action/stage/outcome, optional payload-root name, child exit/timeout, OS error number and response-size/encoding indicators. Reports exclude raw errors, child output, arguments, environment values, private paths and configuration. Diagnostic failures do not alter upgrade/rollback decisions. The disposable Windows smoke runner supplies a fresh directory per invocation, verifies the reports before upgrade, and uploads them with its allowlisted diagnostics; the variable is stripped before service commands.

For a native smoke run against an isolated worktree service, set `NOOTIFY_SMOKE_UI_URL` to its `http://127.0.0.1:<port>/` origin and launch the development binary with `--smoke-test`. Service and update workers are disabled in this mode. Development uses a separate application identity so the installed production app remains available. Verify native window and tray behavior with the actual MyGo application; the browser alone cannot prove native dragging, single-instance activation, close-to-tray, or installer handoff. Both the live service page and embedded offline page retain the fixed titlebar, update, and language bridges. An isolated smoke failure at initial offline readiness reports evaluation categories, native load counts/codes, fixed DOM/image/language fields, UI-thread response and browser-controller availability, Windows apartment/thread ownership categories, and private offline asset HEAD statuses under a shared diagnostic budget. Initial navigation has a separate 30-second cold-start allowance and must finish at the exact offline document before any smoke evaluation starts. The original DOM assertions still use an eight-second wait and two-second evaluations. Diagnostics never record page text, URLs, native descriptions or credentials.

The update worker runs in Go under `desktop/internal/updater`, independently of the native UI thread. It pushes its state into the page as a `nootify-update` DOM event, replayed on every page load, and the page asks for a check or an install by navigating to `nootify://update/check` or `nootify://update/install`, which the window's navigation policy cancels. These are the only update requests; the page still has no IPC. A native initialization script also handles dragging and double-clicking empty title-row areas through the fixed `nootify://window/drag` and `nootify://window/zoom` requests, leaving buttons and links clickable. A plain browser receives neither the script nor update events, so it keeps its ordinary layout and **设置 · 关于** shows only the service version there.

CI runs TypeScript tests, resource staging, Go formatting/static checks, and Go tests for `desktop`, `internal/`, and `native/core` on macOS and Windows. It builds the actual MyGo bundles. Windows additionally exercises named-pipe messaging, task ownership, and process-tree shutdown. Its synthetic `0.0.0` baseline installer comes from the same sources using a package-version override. The runner silently installs it in a path with spaces, launches the installed desktop and daemon, checks single-instance and independent-service behavior, then upgrades to the current package with `/UPDATE /R`. Tests verify task/data retention, service restart, uninstall cleanup, and reinstallation. Artifacts contain the unsigned installer and allowlisted diagnostics, excluding tokens/settings. These disposable-runner checks do not cover SmartScreen, interactive installer clicks, or production signing credentials. To publish a release, update the root `package.json`, commit to `main`, then push a matching `vX.Y.Z` tag. The workflow rejects a mismatched tag. Platform builds produce macOS DMG/updater and Windows NSIS artifacts. Existing updater signing secrets remain compatible inputs for the Go signer, and the public key/signature format is preserved for installed clients. One finalization job validates both platforms and publishes all assets with one `latest.json`; publication is serialized and compares stable semantic versions before changing GitHub's latest designation. An unavailable or unrecognized latest-release response stops promotion. Windows installers are updater-signed but not Authenticode code-signed. A manually dispatched release must select a version tag.

## Install from a source checkout

The packaged app installs its service automatically. For a checkout-based installation instead:

```bash
./build/nootify launchd-install --mcp-config ~/.claude.json
```

On macOS, this creates `~/Library/LaunchAgents/dev.idy.nootify.service.plist` and loads it into the current user's GUI launchd domain. On either supported OS, the platform-neutral install command is:

```bash
./build/nootify service-install
```

Add `--mcp-config` with the explicit path to your `.claude.json` if needed. Windows installs `Nootify.Service.<user-SID>` using the current user's interactive logon token; it runs at login and restarts after failure without administrator access. `service-status`, `service-start`, `service-restart`, `service-stop`, and `service-uninstall` control only the owned Windows task. Running-instance discovery explicitly includes hidden tasks and matches the exact current-user task path; query failures remain errors. Stopping disables the Windows task and waits for its complete owned job to exit; `service-start` or reopening the desktop app re-enables it. `service-uninstall` leaves private settings intact. Use the launchctl commands below to control a macOS job. The executable must remain at its installed path.

Configure named instances on **Channels**. The old single-bot credential sources remain available for migration and compatibility: `LARK_APP_ID`/`LARK_APP_SECRET` for a direct launch, saved legacy Feishu settings, then an explicitly selected `mcpServers.lark` MCP configuration. A launchd job does not inherit your interactive shell environment. Once imported, the provider's saved configuration is authoritative; changing an old credential source does not overwrite it on every startup. Other modules remain available without an enabled provider.

The default private state directory is `~/.local/state/nootify/` on macOS/Linux, or `%LOCALAPPDATA%\Nootify\state` on Windows. The Go core's authoritative state is **`provider-core/state.json`**: its stable node UUID, provider credentials and default, listener configuration/token, session mappings and deletion tombstones, message references/return routes, delivery outcomes, deduplication records, and independent peer queues/confirmations. A private lock prevents two cores from sharing the directory. Each update writes a `0600` temporary JSON file, syncs it, atomically replaces `state.json`, and syncs the directory on Unix. A post-replacement sync failure is reported as `committed_not_durable` (HTTP 409): the published file/memory and live configuration stay consistent, without blind mutation resubmission. Peer publication waits for the durability barrier. The directory uses `0700` on Unix. Eligible completed event/delivery/operation records retain at least seven days, and references at least thirty days; reusing an ID after that terminal horizon is a new admission. Unresolved history, pending/uncertain/retryable work, queued inbox callbacks, peer backlogs and unfinished releases stay protected across restarts. Limits reject new admissions rather than evicting protected work.

Go retains **`state.sqlite`** for local adapter registrations, routing observations, backends, cooperative inboxes, settings, and legacy data. Its incremental transactional saves use WAL and full synchronous commits; the store retains a bounded connection and closes it after admitted work has joined at shutdown. On Unix, the directory is mode `0700` and database/journal files use `0600`. Windows service installation repairs protected DACLs throughout the existing state tree to allow only the current user and SYSTEM. Go startup also protects the active state directory, database and authentication token; cache loading repairs active caches, and new cache/export files receive private DACLs before sensitive data is written. Directory grants inherit to new SQLite sidecars and other children. Startup does not recursively rewrite inactive exports or retired state. Redirected entries are rejected instead of traversed.

Two separate one-time migrations preserve older installations. Go can first import the old root-level version-one `state.json` into SQLite, including unread inbox items and legacy receipts/cursors. Schema creation, rows, and its migration marker commit together; failure rolls back and leaves the source unchanged. SQLite migration 3 preserves the latest 1,000 routing observations; these are historical results and previously active sessions show as unconfirmed after restart. SQLite remains authoritative for Go state and never reimports a stale root-level backup after successful initialization. Independently, the Go core imports available legacy bot credentials and matching-app group bindings, preserves chat IDs, saved adapter identities and agent session IDs, and associates them with its stable node ID. Multiple groups for one session remain independent aliases with their own sender trust. A usable enabled same-app provider owns them when present; otherwise they use `legacy-feishu`. Whole-chat cursors are migrated without treating thread-only progress as chat coverage. An import marker and provider tombstones prevent a later startup from undoing edits or deletions. No credentials means no core import. Startup and reconnect reconcile available Feishu history from those persisted cursors over a finite interval. Failed attempts retry that same interval with cancellation/backoff; synchronized connections do not poll message history. Source deduplication stays protected until the cursor covers unresolved input, including outages longer than the ordinary completed-record horizon. Platform retention, permissions and unavailable history remain explicit recovery limits.

The service reserves its HTTP listener before opening Go state; an occupied-port startup cannot initialize that migration. The source installer validates ownership and waits for the legacy process to finish its final writes and exit before starting the replacement. Keep both stores and the other private files when upgrading; a configuration export is not a conversation-state backup. A newer or corrupt store is reported rather than silently replaced from an old backup.

The separate `auth-token` file and its value are retained, so existing CLI clients continue to authenticate. Configuration exports, logs, and directory caches keep their existing files and formats. Retired feature files remain unused and are not deleted. Retired embedded Tailscale identity files remain unused: Nootify does not read, migrate, or delete them and leaves the operating system's Tailscale installation unchanged. Session inbox tokens must be registered with the independent daemon; they are stored only in private state, never in the repository, group messages, or logs. HTTP responses list public session information without socket credentials.

```bash
./build/nootify health
```

## Register the current session

Run this from the target Claude session so the real `CLAUDE_CODE_MESSAGING_SOCKET` and optional `CLAUDE_CODE_MESSAGING_TOKEN` are available:

```bash
./build/nootify register --session-id local_example --session-name "My session"
```

Registration saves optional inbox credentials for use when the live runtime's socket matches. It does not trigger discovery or add an entry to the routing-history view. When a Claude message arrives, the resolver opens only the named Desktop session record and matches it against the small running-process registry. The full `local_...` ID is matched to `hostSessionId` and `cliSessionId`; unrelated session files are not opened. Archived, missing, offline, and unverifiable sessions are ignored, and stale saved socket paths are never used as a fallback.

For that targeted lookup, Desktop account/profile directories are located under `~/Library/Application Support/Claude-3p/claude-code-sessions` and `Claude/claude-code-sessions` on macOS, or `%APPDATA%\Claude-3p\claude-code-sessions` and `%APPDATA%\Claude\claude-code-sessions` on Windows. Runtime records come from `~/.claude/sessions` (honoring `CLAUDE_CONFIG_DIR`); Windows inboxes use the client's existing named pipe rather than Unix socket filesystem metadata. Before sending authentication or message frames, a native helper checks the connected pipe server's PID against the selected live runtime record and its process-token user SID against the current user. It retains that connection and process handle through the write and uses identification-only impersonation; a missing identity or mismatch fails closed. These local formats may change in later releases. An unverifiable archive field produces `archive_unknown`. Live CLI sessions have no Desktop archive record; inactive CLI sessions are ignored.

## Agent input transports

Each adapter resolves only the incoming ID:

| Adapter | Lookup and archive check | Input transport |
| --- | --- | --- |
| `claude-desktop`, `claude-code` | Targeted local record and live runtime lookup | Existing inbox socket |
| `codex` | Read-only indexed `WHERE id = ?` query in the latest `state_*.sqlite` under `CODEX_HOME` (default `~/.codex`); then resolve that ID through the configured app-server or the existing macOS Desktop owner | Configured app-server WebSocket, or Desktop's local IPC router when no backend URL is configured; accepted input is confirmed by its turn receipt |
| `opencode` | `GET /session/:id` on the configured server; check `time.archived` | `POST /session/:id/prompt_async` |
| `trae`, `workbuddy` | Explicitly registered Nootify conversation ID; native availability/archive state is unknown | Private inbox read by that conversation's `thread-receive`; no automatic wake-up |

Codex never calls `thread/list`, `thread/start`, `thread/resume`, or `thread/unarchive`. A thread not loaded in the selected client is logged as offline. OpenCode never calls its session-list API or creates a session. `input_accepted` means the client accepted the input, not that generation completed. Interactive approval requests are not approved by the bridge.

On macOS, Codex Desktop needs no manual backend address. When no explicit Codex backend is configured, Nootify connects to `CODEX_HOME/ipc/ipc.sock`, verifies its OS-user ownership, discovers the owner of the requested thread and requires an already-resumed conversation. It forwards input through Desktop's versioned local IPC protocol, keeping the original app-server and native tools. The owner first attempts to steer its current turn; only its exact, pre-submission inactive-turn rejection permits starting a new turn. Timeouts, disconnects and invalid input receipts never trigger another submission. The adapter was checked against Codex Desktop's bundled CLI `0.166.0-alpha.5.1`; this IPC is private and can change between Desktop versions. Unsupported method versions fail without submitting input. Windows and standalone clients can use an existing app-server WebSocket.

To select an **existing** local backend explicitly, set its address once, not one configuration per session:

```bash
./build/nootify backend-set --adapter codex --url ws://127.0.0.1:4500
```

```bash
./build/nootify backend-set --adapter opencode --url http://127.0.0.1:4096
```

The Codex port above is an example, not an automatically discovered Desktop endpoint. The app-server must own the target live thread and use the corresponding local `CODEX_HOME`. This tool does not start another Codex process to take over its history. OpenCode defaults to its documented `127.0.0.1:4096` address if none is configured. Add `--directory` when its server needs a project directory.

The CLI reads optional `CODEX_APP_SERVER_TOKEN` or `OPENCODE_SERVER_USERNAME` / `OPENCODE_SERVER_PASSWORD` from its environment and stores them privately with the backend configuration. Direct daemon launches can also use `CODEX_APP_SERVER_URL` / `OPENCODE_SERVER_URL`; launchd does not inherit your shell environment, so use `backend-set` for an installed service. Endpoints are limited to loopback addresses and cannot be supplied by announcement text. No available local session or backend means an explicit ignore reason, never a fallback to Claude.

## Providers and remote nodes

Open **Channels** under **Message bridge** to manage one compact grouped list of configured instances. A text **Add** action sits at the upper left immediately above the list. Each single-line row aligns its name/default badge, type, labeled connection status, enable switch, and text actions; narrow views scroll the list horizontally. The already-default action is hidden and Delete remains visually secondary. IDs and addresses stay in the editor. Empty lists retain centered explanatory text. Add opens a searchable three-choice dialog; choosing a type opens its configuration, and Edit uses the same standard Magpie dialog. The choices map to two underlying provider types:

| Channel choice | Configuration | Role |
| --- | --- | --- |
| Feishu Bot (`feishu`, `connection_type: bot`) | App ID, App Secret, trusted recipient `open_id` | Receives Feishu WebSocket events and manages notification groups/messages |
| Feishu personal app (`feishu`, `connection_type: personal-app`) | Channel name and enabled state, then QR authorization | Registers an app and saves its private bot credentials to a separate channel |
| Remote Nootify (`remote`) | Server `host:port`, token, TLS switch, optional TLS server name | Calls another node's notification API and subscribes to its unmatched incoming events over gRPC |

Multiple instances of either provider type can be enabled together. Personal-app editors hide manual credential fields. The Feishu Bot editor's recipient is a manual `open_id` field; it identifies the user invited to newly created groups and the trusted sender admitted by that provider. Existing secrets/tokens stay masked and a blank secret field preserves the saved value. Ordinary summaries show only whether a secret is set. A provider's type and a Feishu provider's App ID cannot be changed in place, including while disabled or during import. Create another provider to use another app; rotating the same app's secret remains supported. Editing/deleting `legacy-feishu` also synchronizes its compatibility API credentials, recipient, saved configuration, export and contact cache. Active environment credentials are checked before direct provider mutations; conflicting credentials/deletion fail before core commit. Startup reconciliation is separate: same-app secrets rotate in place, while a changed environment App ID reuses a matching provider or creates a deterministic environment instance without rebinding old sessions. Only absent or previously managed defaults switch; explicit named/remote defaults remain selected. Compatibility APIs track the effective provider, and a proven identity conflict exposes an actionable status without stopping other providers. Creating/selecting a matching provider or removing the conflicting identity re-runs reconciliation in the Settings queue and clears the conflict without a restart. Concurrent provider edits cannot bypass environment validation after the active provider changes; an unconfirmed recovery is not blindly resubmitted. If a committed core change cannot be mirrored to Go disk, the API and in-memory mirror follow the committed core, an explicit pending outcome is reported, and recovery retries only local persistence. Exports wait for mirror repair and identical retries do not repeat the provider mutation. A rejected recipient change or proven App ID conflict restores the previous saved state. Deleting a provider closes that instance; it does not delete an agent's original conversation or automatically move existing notification sessions to another provider.

Personal authorization records the channel name and enabled state before showing a focused QR view with the official authorization link, expiry, status, and Cancel. A successful new registration saves a separate channel without replacing existing channels or changing the default. Existing personal channels offer **Reconnect** using stored credentials, same-app reauthorization, and app-specific permission checks; a different App ID is rejected. **Recover previous authorization** restores the original target and sanitized flow after a refreshed/closed page or lost start response. Recovery never starts another flow or resubmits a save. Saving refuses cancellation, completed saves remain inspectable, and an uncertain save exposes its allocated channel ID for checking instead of automatically retrying. QR authorization links and setup checks are local-only.

An **Agent Session** has `{node_id, adapter, session_id, name?, metadata?}`. The core generates a stable node UUID and the bridge supplies it for local sessions. Routing uses the full identity, so equal session IDs on different nodes/adapters are distinct. `Ensure` (`session.ensure`) reuses the existing provider binding; a new session uses an explicit `--provider-id` or the default provider. Changing the default does not move existing sessions. A conflicting provider selection fails instead of silently rebinding. Metadata get/set and `DeleteSession` (`session.delete`) follow that same binding, including across remote nodes. Deletion removes notification resources and mappings, retains a tombstone against replay, and never deletes the native agent conversation. An explicit ensure retries unfinished cleanup before reactivating a deleted notification session. A disabled provider must be made available for cleanup; if the old provider has been removed, an explicit ensure/bind can select a replacement. Retired resource identities remain suppressed so late events from an abandoned destination cannot reach the reactivated session.

Subscriptions also prove a persistent Ed25519 node identity. First connection pins the new peer's public key after a fresh server challenge; a shared listener token alone cannot replay or confirm another pinned peer's queue. Existing peers with an unbound identity keep their backlog but require explicit owner binding. Upgrade both endpoints, then obtain the public identity on the downstream:

```bash
./build/nootify node-identity
```

Verify its node ID and public key out of band, then bind that existing peer locally on the upstream:

```bash
./build/nootify peer-bind --peer-node-id <node-id> --public-key <public-key>
```

These commands support `--state-dir` and `--port`. They never export the private signing key or change the existing node UUID. A conflicting already-pinned key is rejected. Identity management requires an actual loopback HTTP peer and is unavailable to LAN callers and over gRPC. General unary gRPC session/message calls retain the shared-bearer trust model, so only share a listener token with trusted callers; this is not complete per-node authorization for every API.

Listener saves and imports validate/bind the new address and load TLS before committing. Failure leaves the old configuration, socket and subscriptions usable. Certificate reload on the same address preserves authenticated streams, while token rotation cancels old-token RPCs and retains durable replay for reconnect. Disable before changing the TLS mode on an unchanged address. The notification core runs in the Go host process. Service shutdown stops admitting work and drains accepted deliveries before closing the core and releasing state locks.

Configure an upstream server under **Settings → Remote access** (`远程接入`). This page controls this node's gRPC listener; a Remote Nootify provider controls an outgoing connection to another node. The listener is disabled by default and uses `127.0.0.1:9418` by default. The page offers enabled/listen controls, a generated or supplied token with an explicit local reveal action, TLS certificate/key file paths, and downstream peer rows showing node ID/name, connection time, pending count, and last acknowledgment. The certificate and key must both be readable by the service. Public listeners require TLS. Plaintext listeners may bind numeric loopback, private LAN, or wildcard addresses, but accept only loopback and private LAN peers. Outgoing plaintext Remote Nootify connections require a numeric loopback or private LAN IP and verify the connected peer; use TLS for public endpoints or DNS names. Plaintext LAN gRPC authenticates the bearer but does not encrypt traffic. Remote clients authenticate with the listener token, separately from the local HTTP control token. TLS clients verify the server against system trust and use the configured server name, or the address hostname if omitted.

For example, node A can own a Feishu bot while B and C each configure a Remote Nootify provider pointing to A. Each keeps its own session identity when requesting a notification destination through A. When a reply arrives, A delivers a locally owned session locally; otherwise it independently offers the unmatched event to every subscribed downstream. B can handle its own session while C retains and confirms its separate copy. A peer's acknowledgment never consumes another peer's event. A locally owned session that is missing, archived, offline, rejected, or fails delivery remains local; it is not reclassified as unmatched and broadcast elsewhere.

Each admitted event and per-peer pending queue is durable before confirmation. Previously subscribed disconnected peers retain their own pending events and replay them after reconnecting with the same node identity. Stable event IDs, full origin message references, visited-node information, and a hop limit suppress duplicate execution across multiple upstream routes and loops. Multiple feeds from the same Feishu app use the source app/message identity for deduplication. Each peer has a bounded delivery window and a durable cursor into the shared event ledger. When one peer fills its window, healthy peers continue receiving; the slow peer refills from its backlog as it confirms events, including after restart. Global ledger exhaustion rejects new admission rather than discarding admitted events. Ingestion confirmation, downstream confirmation, agent transport acceptance, and explicit session acknowledgment are separate stages. Restarting with an uncertain local agent submission records it as unconfirmed and does not automatically submit it again. Remote replay covers events already admitted to Nootify; event-triggered Feishu history reconciliation separately recovers available input missed during startup/disconnected intervals. Shutdown drains accepted agent deliveries before stopping the core. A lost core response after submission is unconfirmed, while a proven pre-submission/authentication rejection remains safely retryable.

Session operations and outgoing sends/replies are directed along their provider binding or stored return route. They are not broadcast commands. Remote providers connect directly through the host network; see [LAN access](#lan-access) for browser access.

## Bind a Feishu group

Use `thread-open` to ensure the provider's notification destination instead of creating platform routing declarations by hand:

```bash
./build/nootify thread-open --agent claude --session-name "My session" --provider-id feishu-work
```

The Go Feishu provider creates a private group, invites its configured recipient, and stores the full Agent Session identity in provider metadata. New groups carry `nootify-session:v1:<base64url-session-json>` in their description; migrated bindings retain their existing group IDs. These identifiers contain no local inbox socket credentials. Agent adapters are `claude-desktop`, `claude-code`, `codex`, `opencode`, `trae`, and `workbuddy`. `--agent claude` detects the appropriate Claude adapter and complete session ID.

For direct Feishu setup, enable the bot capability, configure **long connection / WebSocket** event delivery, subscribe to the message-receive event (`im.message.receive_v1`), and publish the application's permissions. Ordinary group replies require the applicable group-message permission, such as `im:message.group_msg`; mention-only access does not cover every group reply. Group creation needs `im:chat:create` or `im:chat`, reading group metadata needs `im:chat:readonly`, updating group metadata needs the relevant chat update permission, and progress/replies need `im:message:send_as_bot`. Session deletion also requires permission to dissolve the group. Explicit acknowledgments require `im:message.reactions:write_only` or `im:message`. Nootify does not grant permissions or change the client's inbound controls. Production receives events through the Go SDK's WebSocket client; message-history read scopes are also needed for startup/reconnect catch-up, but do not enable periodic message polling.

Legacy `lark-*` command names and old settings remain compatibility surfaces for existing installations. In particular, `lark-ack` and `lark-reply` can resolve a retained plain Feishu message ID when it is unambiguous. Basic `lark-bind` remains available without metadata flags. The binding HTTP API forwards object metadata into the session and accepts the old CLI default `metadata: announcement` without replacing structured metadata. Unsupported `metadata: message` and `pin: true` reject explicitly. Adoption always checks current descriptions and announcements, including already managed groups, and leaves existing human text untouched; legacy ingress revalidates routing before accepting input. Group adoption checks explicit markers, Desktop IDs, labeled Codex UUIDs and OpenCode IDs across styled announcement text and rejects conflicting/ambiguous declarations or trusted senders. Adoption also requires fresh Feishu source-time evidence from its validation requests; missing or malformed dates reject safely rather than replaying an existing chat from the Unix epoch. Unbound group descriptions cannot authorize incoming messages. New integrations should use provider-aware session operations and full message references. The old hostname-based `agent-session:v1:…` announcement workflow is migration input, not the identity format of newly created core sessions.

### Replying to the original message

The core accepts content as `{text?: string, blocks?: ContentBlock[]}`. Supported block types include paragraph, text, link, and code, with nested children. Feishu text/posts are converted to this format; unsupported message types or post elements are rejected as a whole instead of silently losing content. Remote relays preserve structured content, while existing local agent adapters receive a text representation.

A message reference is `{origin_node_id, provider_id, message_id}`. Its origin and provider ID survive every relay unchanged. Forwarded input includes shell-quoted callback commands using an opaque base64url `--message-ref`; use that exact value so acknowledgments and replies follow the original return path:

```bash
./build/nootify message-ack --message-ref <reference-from-forwarded-message>
```

```bash
./build/nootify message-reply --message-ref <reference-from-forwarded-message> --text "I am here; I will follow up shortly."
```

For multiline replies use `--text-file <path>` or `--text-file -` to read stdin. The forwarded commands include the actual CLI path, private state directory, and service port so they work from another project. Credentials remain local and are not put in the prompt. User message text is not inserted into callback shell arguments. A bare `--message-id` through the legacy commands fails if multiple provider references match it.

An explicit session acknowledgment adds a `FINGERHEART` reaction to the source Feishu message through its return route, without sending a chat message. Agent delivery completion alone is not that callback. The core persists acknowledgment state; a reaction failure does not cause another agent submission. Sending/replying supports `request_id` deduplication in the API: reuse the same ID for the same operation, and never blindly retry an uncertain send with a new ID. By default the local reply endpoint derives a stable ID from the source reference and reply content, so an identical callback reply is deduplicated across retries/restarts. Progress sends without an explicit request ID retain a durable attempt identity while an identical send is pending, retryable, or unconfirmed. A retry cannot duplicate an uncertain submission, including after a restart. After a confirmed success, sending the same text again is a new operation. `thread-send --request-id <id>` lets callers explicitly reuse one attempt across retries. Remote RPCs have a 45-second timeout, and CLI HTTP calls allow 75 seconds for the terminal response. The Go host calls the core in process; there is no production stdio bridge.

Delivery outcomes distinguish `socket_written`/`input_accepted` (**waiting for a session receipt**), cooperative `inbox_queued`, rejected/retryable/unconfirmed completion, and an explicit `session_acknowledged` callback. A downstream's durable confirmation is not a read receipt. Socket writes do not prove that the model admitted or processed the message; verify it in the original session for an end-to-end test. Peer messages cannot approve permission requests.

**Independent-daemon admission:** a launchd process is not a child of the target Claude session. Supplying the session token does not override an explicit process-ancestry verdict on macOS. Claude's inbound policy can therefore hold or refuse messages even after `socket_written`; this particularly affects sessions running with bypass permissions. Unattended delivery requires an inbound policy that explicitly accepts this source, such as an owner-configured `crossSessionInbound: "accept"` in an appropriate settings scope. This service never changes that setting or asserts a sender permission mode.

Clicking a row expands paths, explanations, instruction text, and update actions; its separate checkbox only controls enablement. Ticking an agent creates its configuration directory and prompt file if necessary, then appends provider-aware notification instructions between `<!-- nootify:begin -->` and `<!-- nootify:end -->`; unticking removes that section. A missing directory is shown as unconfigured, rather than used to infer whether the agent is installed. Nothing outside the markers changes, symlinked prompt files are edited at their target, the previous file is copied to `agent-backups/` in the state directory (last ten per agent), and files with unbalanced markers are left alone. "Needs update" means the block differs from what this installation would write, for example after the app moved. Prompts can only be changed from this computer; over the LAN the page is read-only.

The section tells new conversations to use two commands, which find the calling session from the variables each client sets (`CLAUDE_CODE_HOST_SESSION_ID` for Claude Desktop, `CLAUDE_CODE_SESSION_ID` for the Claude Code CLI, `CODEX_THREAD_ID` for Codex). OpenCode does not export its session ID, so its section asks for `--session-id ses_…`.

Trae and WorkBuddy use a cooperative inbox because a supported API for injecting input into a selected existing desktop conversation has not been verified. Start a new conversation after enabling their rules. Run `thread-open --agent trae` or `thread-open --agent workbuddy` with `--session-name` once; Nootify allocates a unique conversation ID and registers its private inbox. Keep the returned `session_id` in that conversation and supply it explicitly on every later `thread-send`, `thread-receive`, and `thread-ack`. Retries of `thread-open` must reuse that ID; failures include it in the error text. IDs are never inferred from the project directory or another agent's environment. At milestones, before asking a question, and before finishing, the instructions ask the agent to run `thread-receive`, process the returned `message.text` using its original-channel receipt/reply commands, then run `thread-ack --message-id <message.id>` for each processed item. Reading does not consume messages, and pending messages survive daemon restarts in private state. Inbox mutations, persistence, and rollback share the state write queue, so a failed acknowledgment cannot be persisted by an overlapping save. Provider messages retain the forwarded full message reference and callback instructions in the inbox text, with their return route held by the core. Legacy inbox items with a Feishu source context retain that context independently of the old bounded history ledger; consuming the item releases that retention. Legacy source callbacks are regenerated on each read with the current service port and bundled CLI paths. Inboxes are limited to 100 pending messages per conversation and 1,000 overall; reads return at most 20 messages and 64,000 bytes. A full inbox rejects new delivery without dropping older input. A queued message is logged as waiting for the conversation to check, never as accepted native input. **This cannot wake an idle or closed conversation**, and it cannot verify the client's native archive state. No native agent session is created or resumed.

```bash
./build/nootify thread-open --agent claude --session-name "Fix login"
```

```bash
./build/nootify thread-send --agent claude --text "Tests pass; the changes are ready for review"
```

`thread-open` ensures the Agent Session's provider binding and reuses it on later calls. A new session uses the default provider unless `--provider-id <id>` is supplied; `thread-send` posts to that binding and accepts the same selector. Use `--text-file -` for multiline text. A remote provider forwards these operations to its upstream without replacing the originating node/session identity. Feishu group names and metadata are managed by the core, so new workflows do not depend on the legacy announcement/name format.

```bash
./build/nootify thread-open --agent claude --session-name "Fix login" --provider-id work-remote
./build/nootify thread-send --agent claude --provider-id work-remote --text "Tests pass"
./build/nootify thread-delete --agent claude --provider-id work-remote
```

`thread-delete` deletes the notification session through its provider, including a remote binding, and preserves a tombstone against replay. It does not delete the original conversation. Repeating deletion is safe; explicitly opening again can reactivate it once resource deletion completes.

The **Go local discovery loop** scans existing conversations at startup and once a minute and backfills missing notification destinations for agents enabled on the Agents page. It uses provider-aware ensure operations and the default provider. This scans local session metadata; it does not poll Feishu messages or copy transcripts. Manual commands continue to work independently of the automatic scan.

Claude Desktop and Codex require an explicitly non-archived metadata record; archived OpenCode sessions are skipped too. Standalone Claude CLI identities come from transcript filenames without reading conversation contents; legacy `agent-*.jsonl` sidechains and nested subagent transcripts are excluded. Trae and WorkBuddy use only their explicitly registered Nootify IDs. Disabled agents are not automatically enrolled. Failed or incomplete Desktop catalogs defer CLI enrollment until their identity maps can be recovered, while verified Desktop records remain eligible. Genuinely absent installations are allowed; non-directory ancestors and broken redirects are treated as incomplete catalogs. Account/profile symlinks and junctions skipped by delivery discovery also mark the catalog incomplete.

Scanning never starts or resumes a native session and does not synchronize its transcript. Delivery still requires the original session to be available. Set the Feishu recipient in each provider editor; `lark-recipient --open-id ou_example` remains a compatibility command for the legacy single-bot configuration. The optional `--channel feishu` argument remains accepted for existing scripts; provider selection uses `--provider-id`, not a new channel name. Codex runs commands in a sandbox: the CLI needs local network access to `127.0.0.1:9417`, so Codex may ask to run it outside the sandbox.

### Message admission and receipts

The Go Feishu provider admits identifiable human-authored text or supported rich posts only from its configured trusted recipient. Bot/application messages are excluded by sender type, independently of which computer sent them. Invalid session/content identities and unauthenticated remote events are rejected at ingress. A remote subscription carries admitted normalized events; its durable confirmation does not authorize a message to target a different session.

Use `message-ack --message-ref …` for an explicit session acknowledgment and `message-reply --message-ref …` for a reply along the original route. Legacy `lark-ack`/`lark-reply` remain compatible for unambiguous IDs. A Feishu acknowledgment uses a `FINGERHEART` reaction; it is a cooperative callback, not proof of model processing. An uncertain local delivery is never automatically resubmitted merely because a remote connection reconnects.

The legacy SQLite database and pending cooperative inboxes remain private local state. Retained old transport records/cursors are history rather than instructions to start retired connections or production history polling. New provider/remote configuration is exported separately from conversation and delivery state. Automated tests use synthetic provider responses and disposable local servers; they do not create real accounts, groups, or external messages.

The embedded startup page retains its local assets under `desktop/`. Numeric counters and progress use tabular figures, and explanatory text has a bounded reading measure. See [shared application controls](ui-components.md) and [DESIGN.md](../DESIGN.md).

The service checks jsDelivr for the latest stable Magpie release in the background at startup and every six hours. It caches only complete releases whose file sizes and SHA256 hashes match the pinned CDN manifest at `STATE_DIR/ui-assets/magpie`, and prefers a cached release only when newer than the bundle. Assets are served from the local origin, so the browser never needs direct CDN access. Versioned stylesheets keep CSS imports and referenced fonts and icon masks on one release; a new stylesheet appears on the next page load. A usable cache or bundled resources keep the application available offline. JavaScript helpers remain owned by Nootify, and no new setting is needed. Maintainers refresh the checked-in baseline with `npm run vendor:magpie`; ordinary builds use the existing bundle without a CDN check. See [bundle provenance](../public/vendor/magpie/README.md) for the exact endpoints and maintenance procedure.

Each collapsed log row stays on one line: a colored message-type label, the message subject as its title, and a consistently neutral action on the right. Message content supplies the subject when available; otherwise it falls back to the session topic or event description. Type colors distinguish user messages, session progress, session replies, and system events independently of delivery outcomes. Actions include Received, Forwarded, Queued, Acknowledged, Replied, Ignored, and Failed, all in the same color. There is no subtitle or second timestamp line; direction, session context, time, diagnostics, and full content remain available in expanded details. Type filters include all records with that label, including failed or ignored messages; the ignore and error filters provide additional action-based views. Outgoing progress (`thread_message`) is not classified as a reply, and forwarding does not imply a session receipt. Search includes translated event labels, source names, sessions, and identifiers, and filter counts follow the current query. Rows expand in place for full IDs, reasons, and message text; logs can be paused and the filtered set exported as NDJSON. The navigation count is the total retained log entries. The routing-session page displays only targets encountered by incoming messages or explicit sends, with their last lookup time and result. Refreshing it performs no client lookups. These are historical observations, not a live inventory.

The page polls a read-only snapshot every two seconds and needs no control token. It accepts loopback and private LAN peers, validates the Host against its own interface IPs or system hostname and service port, and enforces origin/fetch-site checks. The control API remains bearer-authenticated. Logs persist in the private `events.ndjson` file, capped at 1,000 entries; a first launch imports available JSON entries from the prior stdout log. Events explicitly distinguish `received`, `socket_written`, `ignored` with a reason, and failures. For accepted senders, message previews are limited to 240 characters; unknown fields and credentials are not logged. A successful socket write is not proof of model processing.

## Settings

**Settings** at the foot of the navigation opens four pages. Service settings can be read over the LAN, but changes are accepted only from this computer: credentials and imports decide who can reach local sessions. The interface language is a local display preference and can be changed on each device.

| Page | Purpose |
| --- | --- |
| General | Selects the local interface language, including over the LAN |
| Remote access (`远程接入`) | Configure this node's authenticated gRPC listener, token, TLS certificate/key paths, and inspect downstream peers |
| 导入导出 | Export and import the configuration |
| 关于 | App and service versions, update checks, and installation |

**Remote access** replaces Feishu in the Settings navigation. It configures the listener used by downstream Nootify nodes, including its token and TLS files; **Channels** configures the outgoing instances. Both pages expose redacted status over permitted LAN browser access and accept changes only locally. Revealing the listener token requires an explicit local action; private-key contents are never returned. See [Providers and remote nodes](#providers-and-remote-nodes).

**Legacy Feishu setup** remains available at `#/settings/lark` for older integrations and migration. It preserves the old bot/personal-app form, QR authentication, recipient picker, and permission checks. New bot and personal-app channels are configured independently on **Channels**; only the compatibility flow updates `legacy-feishu`. Changing the selected legacy form does not change its active connection until credentials are saved or QR authentication succeeds. Its saved connection type survives restarts and configuration export/import; older settings/files default to Feishu bot.

Personal app authentication uses Feishu's app-registration device flow directly; no `lark-cli` installation, shared Nootify bot, or personal-user OAuth login is required. It starts only after an explicit click. Scan and confirm in Feishu, and Nootify verifies the returned credentials, saves them privately for the selected channel, and uses the scanning user's app-specific `open_id` as the recipient when supplied. The separate legacy route applies those credentials to compatibility settings and the legacy provider. The QR, authorization link and registration progress are available only through same-origin loopback actions. Device codes and returned secrets are never included in ordinary page data or logs. Cancel stops registration polling without replacing the current connection; expiry, refusal and network failures have retry paths. Saving is a local commit and cannot be cancelled halfway through.

A saved app is reused on later launches. In the legacy setup route, **Use existing personal app** exposes manual credential entry and a link to configuration import; it does not discover every app in a Feishu account. To share a bot across computers, configure one upstream Nootify to ingest its WebSocket events and connect the other nodes through Remote Nootify providers. Do not assume Feishu supplies an independent event copy to every direct WebSocket client using the same application. Core migration imports bindings matching the legacy app and preserves their original groups; changing a provider does not grant it access to another bot's groups. Moving configuration alone does not move node identity or conversation state.

Bot connectivity and permissions are separate. The personal-channel editor checks the selected app's required group/message scopes and links missing permissions to the official developer console. The separate compatibility inspector still checks legacy group-announcement read/write, message-reaction write, and ordinary-group-message scopes, with a locally generated console QR and **Check permissions again**. New core groups use provider metadata and WebSocket message events as described under [Bind a Feishu group](#bind-a-feishu-group). The default personal-agent template supports group creation, sending, and messages mentioning the bot, but may not cover ordinary group replies or every metadata operation. An app administrator must enable missing permissions, publish a version and obtain any required approval; scanning alone does not grant those permissions. A failed scope inspection is shown as unconfirmed, not as a successful permission check.

The **legacy manual setup** asks Feishu for a tenant token before saving; this validation belongs to the compatibility flow. It updates that provider without restarting unrelated modules. Legacy environment credentials take precedence within this flow, so saving there is refused while `LARK_APP_ID`/`LARK_APP_SECRET` are set. The active legacy secret appears as a mask; its eye button reveals it through an explicit same-origin, loopback-only POST. Ordinary page data, logs, and LAN clients never receive it, and leaving that page masks it again. Clearing compatibility credentials can fall back to the selected MCP file.

The **provider editor** saves each instance independently to the Go store. It validates required configuration and restarts that provider's connection; a saved form alone does not prove authentication, permissions, or WebSocket readiness. Check the instance's connected/reconnecting/failed status. Its secret/token fields are write-only, and leaving one blank on edit preserves the existing value. New instances do not inherit a global bot secret. Connection status is event/stream based, not the result of a successful history-poll pass.

The **legacy Feishu recipient picker** can accept an `open_id` or select one with **Choose from Feishu**. The Feishu Bot channel editor uses manual `open_id` entry; personal authorization obtains the recipient from the registration response when supplied. This directory picker applies to the compatibility setup. A compact searchable dialog shows real Feishu avatars and nickname plus default name, preserving provider names already formatted as an alias with a parenthesized name. Images load lazily from validated HTTPS Feishu image-CDN URLs; unavailable images fall back to initials. Nicknames are searchable, and the current recipient is pinned. Choosing a row is a draft; **Confirm selection** saves it and returns focus to the picker button. The directory streams useful batches over a local NDJSON response, with at most four provider requests in flight, so already loaded contacts can be searched and selected before traversal completes. Completed snapshots are cached in the private `lark-directory-cache.json` file (0600), scoped to the application and credential identity without storing the App Secret. Fresh snapshots are reused for 15 minutes; snapshots up to 24 hours old appear immediately while a fresh directory is read in the background. The cache survives page and service restarts. An explicit reload or permission retry bypasses freshness, and closing the dialog cancels its pending request. Existing contact rows and decoded avatars are reused across batches, searches, and selection changes; refreshing does not clear a usable list or move its visible scroll anchor. Enable `contact:contact.base:readonly` and `contact:user.base:readonly` and configure the app's contact access range in the Feishu developer console; user-group expansion additionally needs `contact:group:readonly`. Only fields permitted by Feishu are returned, so names can fall back to open_id. Inactive users are omitted when their status is available. Reads are bounded to 20 seconds, 100 API requests, and 5,000 users, with an explicit warning for partial results. Directory data stays in private local storage and is available only through the local UI, never LAN viewers; manual entry remains available if permissions or the network prevent listing users. Missing permissions retain the provider's scope details and an app-matching official console link. The dialog generates its QR code locally and offers retry after setup; partial lists stay usable while optional access is missing. The QR opens app permission settings, not an automatic user OAuth grant: an app administrator may need to publish a version and obtain approval, and contact visibility is configured separately.

**Import/export** (`导入导出`) writes `exports/nootify-config-<time>.json` in the state directory, mode `0600`, keeping the newest ten. The file includes **all provider instances and their credentials/tokens**, the default provider, remote listener configuration and token/TLS file paths, legacy Feishu settings when present, Codex/OpenCode connections, and enabled agents. **It contains plaintext secrets and is written only to a private file**; the page receives its path and a redacted summary rather than the document. The summary can show provider counts and public IDs, never secrets.

Exports do not include the node UUID, notification-session bindings/tombstones, message/delivery records, peer queues, native agent conversations, or retired VPN identity/enabled state. TLS file paths are configuration; certificate/private-key contents are not copied. Importing on another computer therefore requires its own session enrollment and readable TLS files and does not adopt the old node's routing identity.

Importing validates the file and previews its changes without showing secrets before applying it. A provider configuration section replaces the provider set, default, and listener configuration as a unit; this can close removed instances and restart configured connections. Other settings are applied only when named in the file, and agents listed are enabled without disabling others. Credential fields are not an online permission check; connection failures appear after application. Listener TLS paths must pass the core's local file validation. Older Feishu-only files remain migration/compatibility input. Retired PR sections and transport fields in older backups are ignored; newer file versions are refused.

## LAN access

Nootify serves HTTP directly on all IPv4 interfaces at `0.0.0.0:9417` by default (`--port` changes it). From the service computer, open `http://127.0.0.1:9417/`. On another device on the private LAN, open the LAN address shown in the sidebar, normally `http://<LAN-IPv4>:9417/`. The snapshot exposes this address as `access.lan_url`. Allow the service port through the host firewall for the intended private network if needed.

When the operating system's Tailscale client assigns this computer an IPv4 address in `100.64.0.0/10`, the same listener accepts connections on it automatically. The local sidebar shows a separate Tailscale address, `http://<Tailscale-IPv4>:9417/`, exposed as `access.tailscale_url`. Addresses are discovered again on each snapshot, so connecting Tailscale after Nootify starts needs no service restart. Disconnecting removes the address on the next snapshot. Both devices must be connected to the same tailnet with access permitted by Tailscale grants/ACLs and the host firewall on the configured TCP port (normally 9417). No additional Nootify login, VPN enrollment, port forwarding, Tailscale Serve, or Funnel setup is needed. Use the numeric address shown in the sidebar; arbitrary DNS aliases, including MagicDNS names, are not accepted as HTTP Host values.

The service checks the actual socket peer and accepts loopback or private LAN addresses. Peers in Tailscale's shared IPv4 range are additionally accepted only when the connection's actual local socket address is also in that range; a CGNAT source reaching an ordinary LAN or loopback address is rejected. Nootify relies on the operating system's Tailscale routing and access controls rather than querying its account or managing its client. Host validation requires an actual private LAN or Tailscale IPv4 address assigned to this computer, or its system hostname, together with the service port; loopback hosts are accepted only from actual loopback peers. Arbitrary DNS aliases and forwarded headers do not establish authority. Origin and fetch-site checks remain enforced.

LAN and Tailscale browser access is read-only. Provider/settings mutations, agent edits, contact-directory reads, and secret reveal require an actual loopback peer. The desktop opens its encrypted gateway automatically; local browser owners can edit directly at the loopback URL or optionally use `ui-url`. Every `/v1/` endpoint requires the bearer token and permits these LAN/Tailscale callers, except `/v1/remote/` identity inspection/binding, which remains loopback-only.

Direct LAN HTTP is plaintext, including bearer-authenticated HTTP requests. Connections to the Tailscale address travel through the operating system's encrypted Tailscale network; Nootify still serves HTTP on that address. The desktop/CLI gateway's authenticated encryption does not apply to direct LAN browser or API traffic. Remote Nootify gRPC is a separate authenticated listener configured under **Settings → Remote access**; numeric loopback/private LAN endpoints may use plaintext, while public endpoints require TLS.

Nootify has no embedded VPN device, enrollment page, tunnel, or listener-publication layer. Retired embedded Tailscale state is left untouched and unused; it is not read, migrated, or deleted. The operating system's Tailscale installation is unchanged. The LAN URL exposes Nootify only, not other previews or files on this computer; share those through a separately configured and verified reachable address.

## HTTP service API

The Go CLI and local tools use the existing JSON HTTP endpoints. Read the bearer token from the private state file in your local application; never embed it in source or browser code. The former Go SDK is no longer distributed. Browser-only TypeScript declarations describe UI responses, while Go packages own all backend routes and lifecycle behavior. `/health` includes `"backend":"go"`, and `/v1/services` lists the enabled modules.

| Endpoint | Purpose |
| --- | --- |
| `GET /health` | Host and module health, without credentials |
| `GET /v1/services` | Installed module names and statuses |
| `GET /` | Browser UI; actual loopback access enables local settings, while LAN settings stay read-only |
| `GET /ui/api/snapshot` | Recent sanitized logs, module health, encountered targets, optional channel status, and LAN/Tailscale URLs (`access.lan_url`, `access.tailscale_url`) |

| `GET /ui/api/providers` | Core node ID, redacted provider instances/default/listener summary, and editable flag |
| `POST /ui/api/providers` | Save a provider, or delete/default/reconnect by `id`; reconnect uses stored credentials without switching the default. UI header and loopback only |
| `POST /ui/api/providers/registration` | Start with `{"action":"start","name","enabled","id"?}`, query/cancel with `registration_id`, or explicitly `{"action":"recover"}` without it; returns only the sanitized flow and original target. Local UI header and loopback only, including status/recovery |

| `DELETE /v1/threads/:session_id` | Delete notification resources/mapping through `{"adapter", "provider_id"?}`; never deletes the native conversation |
| `GET /v1/threads/:session_id/metadata`, `PUT /v1/threads/:session_id/metadata` | Get/set provider session metadata; PUT takes `{"adapter", "provider_id"?, "metadata":{…}}` |

| `GET /v1/lark/recipient`, `PUT /v1/lark/recipient` | Read or set the Feishu recipient's open_id |
| `GET /v1/sessions` | Latest 1,000 routing observations, restored from SQLite across restarts; never queries clients |
| `PUT /v1/backends/:adapter` | Configure an existing local Codex or OpenCode endpoint |
| `PUT /v1/sessions/:id` | Register/update an inbox from an authorized local client |
| `POST /v1/sessions/:id/messages` | Send attributed text to a registered inbox |
| `POST /v1/lark/messages/:id/ack` | Legacy acknowledgment by an unambiguous retained message ID |

| `GET /v1/lark/bindings` | Compatibility view of Feishu group/session bindings |

Local UI mutations and secret reads require `X-Nootify-UI: 1`, Host/origin/fetch-site checks, and an actual loopback peer; no authorization link is needed for direct loopback pages, including after reload. LAN viewers cannot mutate UI state or read local secrets. `GET /v1/remote/identity` and `PUT /v1/remote/peers/:node_id` expose owner-only identity inspection/binding on loopback; the latter takes `{"public_key":"…"}`. Provider summaries expose App IDs, recipient IDs, addresses, TLS settings, and secret/token presence flags; they omit credential values. The in-process core API is private to the Go host; stdio is retained only for compatibility fixtures. Remote gRPC callers can invoke session/message operations, not private provider configuration, exports, listener-secret reads, or local agent socket registration. See [provider-protocol.md](provider-protocol.md) for the RPC frames and durable routing contract.
